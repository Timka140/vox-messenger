# Vox Cluster — контракт координации между VPS

Версия: 1.0 (утверждён Тимом 2026-09-16).
Исполнитель: отдельная модель. Этот документ — единственный источник требований.
Каждый этап (§13) реализуется через отдельный план (plan mode), с живой
проверкой на двух узлах и коммитом. На VPS ничего не менять до утверждённого
плана этапа.

## 0. Цель и рамки

Несколько VPS («узлов») делят между собой нагрузку по клиентам. Любой узел может
пропасть в любой момент. Координацию (кто где, маршрутизация сигналинга,
групповой relay) выполняют сами узлы. Клиент подключён ровно к одному узлу и не
знает, на каком узле его собеседник.

Сейчас узлов два:

| Узел | Адрес |
|---|---|
| vps1 | n1.northwindcdn.com |
| vps2 | n2.northwindcdn.com |

SSH-доступ — `build/remote/<node>/ssh.conf` (не в git).

Не входит в объём (see §12): Kademlia/DHT, федерация с чужими операторами
(gestalt), офлайн-хранилище личных сообщений на сервере.

**Совместимость:** пользователей у программы пока нет, поэтому обратная
совместимость со старыми клиентами не требуется. Клиент и сервер выпускаются
вместе, поля протокола можно менять без legacy-веток. Семантику существующих
сообщений всё же не менять без нужды: меньше правок в клиенте.

## 1. Термины

- **Узел** — процесс `signal-server` на одном VPS. `node_id` = hex Ed25519
  публичного ключа сервера (тот же ключ, что клиент пиннит по TOFU).
- **Кластер** — множество узлов, перечисленное в конфиге каждого узла.
- **Линк** — постоянное WebSocket-соединение (`ws://`, без TLS) узел ↔ узел.
- **Каталог** — реплицируемая таблица «pubkey клиента → узел».
- **Домашний узел клиента** — узел, к которому клиент подключён сейчас.

## 2. Топология и линки

- Полный граф. Расчёт на N ≤ 8 узлов, репликация полная.
- Адрес узла — `ws://<имя узла>:9741/ws` (тот же порт, что у клиентов; TLS нет,
  подлинность узла обеспечивает подпись Ed25519). Pubkey узлов:
  `build/nodes/<node>.conf`, поле `NODE_PUBKEY`.
- Конфиг узла — переменные окружения сигналки в `cluster.env` рядом с `.env`
  (генерирует `build/deploy-signal.sh` из `build/nodes/*.conf`):
  ```bash
  CLUSTER_SELF_ADDR=ws://n1.northwindcdn.com:9741/ws   # как этот узел виден снаружи
  CLUSTER_PEERS='ws://n1.northwindcdn.com:9741/ws=<pubkey>;ws://n2.northwindcdn.com:9741/ws=527534742f96d8b8f76930edc155956533f66c71558f8e40498fd34992703265'
  CLUSTER_SOFT_LIMIT=400                               # см. §6.3 redirect
  ```
  Себя в `CLUSTER_PEERS` можно не исключать. Узел с pubkey не из списка линк
  не получает (allowlist).
- Инициатор линка — узел с лексикографически меньшим `node_id`; второй только
  принимает. Так между парой всегда ровно один линк.
- Аутентификация линка — тот же challenge/подпись, что у клиентов, но в обе
  стороны. Принимающий узел ещё не знает, кто подключился, и шлёт обычный
  `challenge` со своим `server_pubkey`. Инициатор сверяет pubkey с конфигом и
  отвечает `node_auth {node_id, signature, client_challenge}`. Принимающий
  проверяет allowlist, подпись и правило «инициатор меньше» и отвечает
  `node_auth_ok {server_signature}`; инициатор проверяет подпись. Отдельного
  `node_challenge` нет. Ключи узлов заранее известны из конфига, TOFU для
  линков не используется.
- Heartbeat: `node_ping` каждые 5 с, линк считается мёртвым через 15 с без
  ответа. Переподключение с экспоненциальной паузой 1 → 30 с.
- Линк идёт на тот же WS-порт, что и клиенты. Первое сообщение от
  подключившегося (`node_auth` вместо `auth`) переводит соединение в режим
  линка. Отдельный порт и firewall между узлами не нужны.
- Все сообщения по линку — JSON того же формата `protocol.Message`
  (`type`, `payload`), новые типы с префиксом `node_`.
- Часы узлов должны быть синхронизированы (NTP). Допустимый разброс 2 с.

## 3. Каталог

### 3.1 Запись

```go
type Entry struct {
    PubKey    string   // клиент
    NickTag   string
    NodeID    string   // домашний узел
    SessionID string   // uuid соединения, выдаёт домашний узел
    TSms      int64    // время auth_ok по часам домашнего узла
    Private   bool     // false — клиент без watch-списка, статус виден всем
    Watch     []string // кому виден статус «в сети» (текущий presence-список)
}
```

`Watch` — тот же список, что клиент присылает в `auth` и `presence_watch`.
Он нужен всем узлам, чтобы каждый фильтровал presence локально (§4).

### 3.2 Интерфейс

```go
type Directory interface {
    Publish(e Entry)                       // локальный клиент прошёл auth
    Update(pubKey string, watch []string)  // presence_watch / update_nick_tag
    Remove(pubKey, sessionID string)       // локальный клиент отключился
    Lookup(pubKey string) (Entry, bool)
    LookupNickTag(nickTag string) (Entry, bool)
    Subscribe(fn func(ev Event))           // Put / Update / Del, все узлы
}
```

Реализация v1 — `fullrepl`: полная копия на каждом узле. Kademlia в v1 не
делается; интерфейс выбран так, чтобы её можно было подставить позже без правок
хаба.

### 3.3 Репликация

| Сообщение | Когда | Payload |
|---|---|---|
| `node_dir_put` | Publish / Update | `Entry` |
| `node_dir_del` | Remove | `{pubkey, session_id}` |
| `node_dir_snapshot` | сразу после `node_auth_ok` в обе стороны | `{entries: []Entry}` |

Правила:

- Конфликт (один pubkey на двух узлах): побеждает больший `TSms`, при равенстве
  больший `NodeID`. Проигравший узел закрывает свою сессию с ошибкой
  `session_replaced` и шлёт `node_dir_del` для неё.
- `node_dir_del` с чужим `session_id` игнорируется (защита от гонки
  «отключился старый, подключился новый»).
- Потеря линка с узлом X: через 15 с (grace) все записи с `NodeID == X`
  удаляются локально, как будто пришли `node_dir_del`. Если X вернётся, snapshot
  восстановит его записи.
- Надгробие: после удаления записи узел хранит `{pubkey, watch}` 24 ч, чтобы
  отвечать на `peer_offline_err` по прежней политике (текущее поведение
  `hub.lastPolicy`, только теперь на всех узлах).

## 4. Presence и поиск

- Presence полностью выводится из событий каталога. На каждое `Put`/`Del`/
  `Update` узел проходит по своим локальным клиентам: кто есть в `entry.Watch`,
  тому `peer_online` / `peer_offline`; при `Update` — разница списков, как
  сейчас в `broadcastStatus` (появился в списке → online, пропал → offline).
- Клиент ничего нового не получает: те же `peer_online`/`peer_offline`.
- `peer_search` — точное совпадение `nick#tag` по каталогу целиком, то есть
  находит и клиентов других узлов.

## 5. Маршрутизация сигналинга

Затрагиваемые типы: `offer`, `answer`, `ice`, `call_*`, `friend_*`.

Алгоритм `Route(msg, from)` на домашнем узле отправителя:

1. Адресат локальный → доставить как сейчас.
2. Иначе `Lookup(msg.To)`:
   - найден на узле X → `node_fwd {from_pubkey, msg}` на X. Узел X доставляет
     локальному клиенту; если клиента уже нет — отвечает
     `node_fwd_err {from_pubkey, to, code}` и исходный узел превращает это в
     `error` с `ErrPeerOffline` для отправителя по текущим правилам
     `offlineVisibleTo`.
   - не найден → `peer_offline_err`, видимость по надгробию (§3.3).
3. Линк на X мёртв, но записи ещё не вычищены (grace) → как «не найден».

Инвариант: клиент не получает ошибок, которых нет сейчас; кросс-узловая
доставка для него неотличима от локальной.

## 6. Клиент: выбор узла и балансировка

### 6.1 Список узлов

- В бинарник зашиты оба узла с pubkey (сейчас список только в БД). Порядок не
  важен, см. 6.2.
- После `auth_ok` узел присылает `server_list {nodes: [{addr, pubkey}]}` со
  всем кластером. Клиент сливает его в `signal_servers` с пометкой
  `source = 'cluster'`: записи с этой пометкой заменяются списком целиком,
  добавленные пользователем вручную не трогаются. Принимается только от
  аутентифицированного узла.

### 6.2 Выбор при подключении

1. Клиент параллельно делает `GET /healthz` на все известные узлы, таймаут 3 с.
   Ответ: `{node_id, clients, soft_limit, links: [{node_id, alive}]}`.
2. Кандидаты — ответившие. Оценка = `rtt_ms + 100 * max(0, clients - soft_limit)`.
   Выбирается минимальная. Ничья — случайно.
3. Если никто не ответил — прежнее поведение: перебор списка по очереди.
4. Липкость: последний успешный узел получает бонус −50 мс, чтобы не прыгать
   между узлами при равном RTT.

### 6.3 Redirect со стороны узла

Узел вправе ответить на `auth` сообщением `redirect {addr, pubkey}` вместо
`auth_ok`, если `clients > soft_limit` и в кластере есть живой узел с меньшей
нагрузкой. Клиент следует redirect не более одного раза за попытку
подключения. Так балансировку в итоге контролируют узлы, а не клиент.

Уточнения реализации (Э2):
- redirect получает только клиент, приславший в `auth` поле `redirect_ok:
  true`. Старый клиент без него получает обычный `auth_ok` и не застревает.
- В `redirect` есть `server_signature` — подпись `client_challenge`, как в
  `auth_ok`. Клиент принимает redirect только с верной подписью.
- Условие на узле: `clients >= soft_limit` (новый клиент был бы лишним), цель —
  живой сосед с наименьшим числом клиентов, меньшим своего. Нагрузку соседей
  узел знает из `node_ping` / `node_pong` (поле `clients`).
- `server_list` приходит отдельным сообщением сразу после `ice_servers`.

### 6.4 Переподключение

Существующий reconnect-loop сохраняется, но на каждой итерации заново выполняет
6.2. Ожидание: после падения узла клиент оказывается на другом не позже чем
через 30 с.

## 7. Групповой relay

Сейчас: одна таблица сообщений с `seq` на группу, dedup по
`(group_id, author_key, client_msg_id)`, клиент синхронизируется с
`last_seen_seq`.

### 7.1 Решение: журнал на узел (multi-master, single-writer per log)

- Каждый узел ведёт **свой** журнал сообщений группы: `seq` выдаёт только тот
  узел, который принял сообщение от клиента. Ключ сообщения —
  `(group_id, origin_node, seq)`.
- Каждое принятое сообщение и каждое изменение состава реплицируется на все
  узлы: `node_grp_msg {group_id, origin_node, seq, author_key, client_msg_id,
  payload, encrypted, server_ts_ms, client_ts_ms}`,
  `node_grp_members` (строки `{group_id, pubkey, is_admin, removed, ts_ms, actor}`).
  Репликация идемпотентна: повтор по ключу игнорируется.
- Состав группы: LWW по `ts_ms` на пару `(group_id, pubkey)`, при равенстве
  побеждает старшее значение: удаление > админ > участник (§7.4). Проверка
  прав администратора делается на принимающем узле, как сейчас.
- Регистрация группы (`group_register`) реплицируется строками состава в
  `node_grp_members`; повторная регистрация с другого узла — no-op.
- При установке линка узлы обмениваются `node_grp_state` — группы, составы и
  максимальные `seq` по каждому `(group_id, origin_node)` — и досылают друг
  другу недостающие хвосты пачками `node_grp_msgs`.

Почему так: нет «домашнего узла группы», а значит нет выбора нового домашнего
при падении и нет split brain. Журнал каждого узла пишет только он сам, поэтому
реплики всегда согласованные префиксы.

### 7.2 Протокол с клиентом

- `group_message_new` получает поле `origin_node` (hex).
- `group_message_send` подтверждается копией `group_message_new` самому автору
  (с `client_msg_id`, `origin_node`, `seq`; §7.4). Клиент повторяет отправку с
  тем же `client_msg_id`, если подтверждения нет за 10 с или соединение оборвалось. Гарантия:
  at-least-once на сервере, exactly-once после dedup.
- `group_sync` вместо `since_seq` несёт `cursors: {origin_node: seq}`.
  Неизвестный узел в курсорах отсутствует → его журнал отдаётся с 0.
  Legacy-ветка для `since_seq` не делается (§0).
- `group_sync_result` отдаёт сообщения всех журналов, отсортированные по
  `server_ts_ms`, с `origin_node` и `seq` у каждого.
- Клиент хранит курсоры per `(group_id, origin_node)` вместо одного `seen`
  (таблица/поле в SQLite клиента, миграция без сохранения старых `seen`:
  после обновления клиент синхронизируется с 0, dedup по `client_msg_id`).
- Тело сообщения — до `GROUP_MAX_MSG_BYTES` = 32 КБ (после разбора JSON;
  кадр websocket ограничен 64 КБ, клиент проверяет оба предела до отправки).
  Отказ `group_message_send` несёт `group_id` и `client_msg_id` отклонённого
  сообщения. Окончательные: `message_too_large`; `not_group_member` и
  `group_not_found` — неотправлено, повтор руками (состав доезжает до узла
  асинхронно). Остальные коды временные, клиент продолжает повтор. Повтор
  уже принятого сообщения от автора, удалённого из группы, получает
  сохранённую копию, а не отказ.
- `group_sync_hint {group_id}` — узел получил догоном сообщения группы.
  Поштучно такие сообщения клиентам не рассылаются (переполнили бы очередь
  пира), клиент в ответ делает `group_sync`. Подсказка отложенная: одна на
  группу после ~500 мс тишины в догоне.

### 7.3 Что теряется при падении узла

Сообщение, которое узел принял и подтвердил, но не успел реплицировать до
падения, недоступно, пока узел не вернётся (тогда snapshot дошлёт). Окно —
задержка репликации, миллисекунды. Это осознанное допущение v1.

### 7.4 Уточнения реализации (Э3)

- Репликация идёт четырьмя сообщениями: `node_grp_msg` (живое сообщение
  своего журнала), `node_grp_members` (строки состава после register / add /
  remove), `node_grp_state` (группы и головы журналов `{origin: max_seq}`;
  при подъёме линка — с составами, а при живом линке раз в
  `AntiEntropyInterval` = 5 мин — без составов), `node_grp_msgs` (пачки до
  200 сообщений, которых нет у соседа, из любых журналов). Отдельных
  `node_grp_register` и `node_grp_snapshot` нет. Периодическая сверка
  досылает то, что иначе ждало бы переподключения: остаток догона сверх
  лимита, потерянную пачку, расхождение голов после очистки. Пропуск ниже
  головы журнала она не видит.
- Принимающий узел пишет пачку реплик одной транзакцией (при сбое — построчно)
  и рассылает клиентам поштучно только живые `node_grp_msg`; на догон
  (`node_grp_msgs`) участники получают `group_sync_hint` (§7.2).
- Состав: LWW по участнику, строка хранит `updated_ms`, `removed` и
  `is_admin`; при равном времени побеждает старшее значение: удаление >
  админ > участник. Полный порядок нужен потому, что равное время здесь
  обычное дело: своё изменение получает время не раньше последнего изменения
  группы, и после одного изменения оба узла считают для следующего одно и то
  же время. У удалённой строки `is_admin` не хранится. Регистрация задаёт
  полный список: кого нет в списке — удаляется; полный список применяет
  только админ уже известной группы.
- `seq` своего журнала — `MAX(seq)+1`, а `server_ts_ms` под тем же замком
  подтягивается до времени предыдущей строки (в пределах 5 мин), так что
  порядок времени в журнале совпадает с порядком `seq`. Очистка по сроку
  хранения оставляет последнюю строку каждого журнала: иначе `MAX(seq)`
  откатился бы и узел выдал бы занятые номера заново. Запись в журнал,
  рассылка своим и реплика соседям идут под замком группы — в порядке `seq`.
- Подтверждение — собственная копия `group_message_new` автора (сервер
  рассылает сообщение и автору, в ней `client_msg_id`, `origin_node`, `seq`).
  Отдельного `group_message_ack` нет. Клиент повторяет неподтверждённое
  через 10 с до 5 раз и после каждого переподключения (таблица
  `group_relay_pending`).
- `group_sync` без `cursors` отклоняется `invalid_message` (§7.2: legacy-ветки
  нет). Выборка по курсорам сливает журналы по времени, беря из каждого
  непрерывный префикс.
- Схема `groups.db` версионируется `PRAGMA user_version`; при переходе на v1
  старые сообщения попадают в журнал своего узла.

## 8. Прочие сервисы узла

| Сервис | Правило |
|---|---|
| TURN (coturn) | На каждом узле свой. `ice_servers` выдаёт узел, к которому клиент подключён. Учётные данные `vox:<pass>` одинаковые на всех узлах. |
| SFU | На каждом узле свой, конфиг из `auth_ok` домашнего узла. Участники одного голосового канала на разных узлах — вне объёма v1 (SFU-звонок работает только если все на одном узле; иначе P2P mesh, как сейчас). |
| Релизы (`releases_dir`) | `release.sh` выкладывает на все узлы из списка `RELEASE_NODES`. Manifest идентичен. |
| Логи (`log_push`) | Только от клиентов с включённой настройкой, под анонимным id `anon-<16 hex>` (не ник). Хранятся на узле, который их принял, в пределах `DEBUG_MAX_TOTAL_MB` / `DEBUG_MAX_AGE_DAYS` / `DEBUG_KEEP_PER_SOURCE` (по умолчанию 1024 / 14 / 10); приём включается `DEBUG_PORT`. Debug API остаётся per-node. |

## 9. Сценарий отказа узла (обязательное поведение)

Клиенты A (vps1) и B (vps2), друзья, идёт звонок.

1. vps1 падает.
2. vps2 через ≤15 с теряет линк, ещё через 15 с вычищает записи vps1 → B
   получает `peer_offline A`.
3. A по reconnect-loop (§6.4) подключается к vps2 не позже 30 с →
   `node_dir_put` не нужен (локальный), B получает `peer_online A`.
4. Звонок переустанавливается клиентами по существующей логике ICE-restart.
5. vps1 возвращается: линк, `node_dir_snapshot` (пустой с его стороны),
   `node_grp_state` + `node_grp_msgs` досылают журналы в обе стороны. Клиенты остаются на
   vps2, пока сами не переподключатся.

## 10. Наблюдаемость

- `GET /healthz` (без auth): `{node_id, clients, soft_limit, dir_size,
  links: [{node_id, alive, rtt_ms, last_seen_ms}]}`.
- Лог узла: события линка (`link up/down`), размер snapshot, конфликты
  каталога (`session_replaced`), redirect с причиной. Уровень Info.
- Метрика в отладочных строках: время от `link down` до полной очистки
  каталога.

## 11. Безопасность

- Линк принимается только от pubkey из `cluster.peers`, обе стороны
  подписывают challenge.
- `server_list` и `redirect` клиент принимает только от аутентифицированного
  узла, pubkey нового узла пиннится сразу (без TOFU-окна).
- `node_fwd` не обходит проверки хаба: получающий узел применяет те же
  правила (blocklist адресата, `offlineVisibleTo`), что и для локальных.
- Watch-списки в каталоге видны всем узлам кластера. Это приемлемо: узлы одного
  оператора.

## 12. Не входит в v1

- Kademlia/DHT, discovery узлов вне конфига.
- Федерация с чужими операторами (docs/gestalt.md заморожен).
- Серверное хранение личных сообщений для офлайн-адресатов.
- SFU-канал с участниками на разных узлах.
- Автоматическое добавление узлов: новый узел = правка конфига на всех + рестарт.

## 13. Этапы и критерии приёмки

Каждый этап — отдельный план, живая проверка на двух узлах, коммит.

**Э1. Линк + каталог + маршрутизация + presence.**
Приёмка: тест-клиенты Alina на vps1, Test3b на vps2. Поиск по точному тегу
находит. Звонок между ними проходит. `kill` сигналки на vps1 → сценарий §9
укладывается в тайминги. Серверные тесты: конфликт сессий, grace-очистка,
надгробие, `node_fwd_err` → `peer_offline_err`.
**Статус: выполнен 2026-09-16.** Пакет `server/signal/internal/cluster`, линк
инициирует vps2 (меньший node_id), RTT ~28 мс. Живая проверка: Alina на vps1,
Test3b на vps2 — взаимный статус, поиск по тегу, сообщение, звонок. Остановка
vps1: Alina на vps2 через 7 с, Test3b ни разу не увидел её офлайн (новая
сессия вытесняет запись упавшего узла раньше grace), звонок не оборвался;
vps1 вернулся — линк через 8 с, snapshot выровнял каталоги. Список узлов
генерирует `deploy-signal.sh` в `cluster.env`. Тестовый клиент сажается на
узел переменной `VOX_SIGNAL_SERVERS` (только `ENV=local`). Группы серверного
relay между узлами — Э3.

**Э2. Клиент: /healthz, выбор узла, redirect, server_list, зашитые узлы.**
Приёмка: с пустой БД клиент находит оба узла; при `soft_limit_clients: 1` на
vps1 второй клиент уходит на vps2 через redirect; ручной сервер в списке не
затирается.
**Статус: выполнен 2026-09-16.** Клиент: оба узла в `KnownSignalServers`,
колонка `signal_servers.source` (builtin / manual / cluster, миграция 64),
выбор узла по `/healthz` (`network_select.go`), общий перебор с одним
переходом по redirect для `Connect` и `ReconnectSignal`. Сервер: `server_list`
после `ice_servers`, redirect по `redirect_ok`, нагрузка соседей в heartbeat.
Живая проверка: клиент без закреплённого списка опросил узлы (vps2 44 мс,
vps1 94 мс) и выбрал vps2, при переподключении выбор повторяется с бонусом
последнему узлу; ручной адрес пережил `server_list` и стоит в конце перебора;
при `SOFT_LIMIT=1` на vps1 второй клиент получил redirect и за 70 мс
подключился к vps2, клиенты на разных узлах видят друг друга. Настоящие
клиенты получат выбор узла с ближайшим релизом клиента.

**Э3. Групповой relay с журналами на узел.**
Приёмка: группа ≥ порога, участники на разных узлах, сообщения доходят всем,
`group_sync` после переподключения на другой узел не теряет и не дублирует
(dedup по `client_msg_id`). Падение узла во время отправки → повтор по ack.
**Статус: выполнен 2026-09-16.** Сервер: журнал на узел в `groupstore`
(схема v1), LWW-состав, репликация `node_grp_*`, fan-out реплик своим
участникам, курсоры в `group_sync`. Клиент: `origin_node` и уникальный индекс
`(group_id, origin_node, seq)`, курсоры `group_relay_cursors`, повтор
неподтверждённых. Живая проверка на группе «Тест-3b»: Alina на vps1 и Test3b
на vps2 обменялись сообщениями через relay (seq 2 из журнала vps1 и seq 1 из
журнала vps2, оба сохранились); при остановленном vps2 Alina написала
сообщение, после старта vps2 обмен состоянием дослал его, и Test3b получил
его через 5 с по курсорам без дублей. Первый обмен состоянием догнал 31
сообщение vps2 и 1 сообщение vps1. Повтор неподтверждённых проверен
тестами клиента.

**Э4. Инфраструктура vps2.**
coturn с теми же учётными данными, `releases_dir`, `release.sh` на оба узла,
`start-signal.sh`/`stop-signal.sh` как на vps1, бэкап бинаря перед выкладкой.
Приёмка: `turnutils_uclient` на vps2 даёт allocation; автообновление с vps2
показывает тот же manifest.
**Статус: выполнен 2026-09-16.** Узлы описаны в `build/nodes/`, секреты в
`build/remote/<node>/`, деплой `NODE=<node> ./build/deploy-*.sh`, первичная
настройка `build/setup-node.sh`, релизы `release.sh` на все узлы +
`build/sync-releases.sh`. Сервисы vps2 работают от пользователя `vox` в
`/home/vox/vox`; coturn vps2 релеит только в публичные сети, relay 52000–59999.

Порядок: Э4 (без линка, просто второй одиночный узел) → Э1 → Э2 → Э3. Э4 первым,
потому что даёт площадку для живых проверок остальных этапов.

## 14. Принятые решения (Тим, 2026-09-16)

1. Цель — распределение нагрузки между равноправными узлами, любой узел может
   пропасть в любой момент, координацию выполняют узлы.
2. `soft_limit_clients = 400` на узел (1 ядро / 1 ГБ).
3. Обратная совместимость со старыми клиентами не требуется: пользователей нет,
   клиент и сервер выпускаются вместе.
4. Линк узел↔узел на том же WS-порту.
5. Групповой relay — журналы на узел (§7.1), без «домашнего узла» группы.
6. Kademlia/DHT не реализуется; интерфейс `Directory` оставляет такую
   возможность на будущее.
